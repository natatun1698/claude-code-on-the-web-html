# 公正競争規約Q&Aチャットボット(kiyaku-qa)

医療機器業公正競争規約(医療機器業公正取引協議会)についてユーザーの質問に
根拠条文つきで答えるチャットボット。既存の `/kiyaku-qa/` を拡張するか、
他業界の規約で同種アプリを新設する際にこのスキルを使う。

## 絶対条件

- **完全クライアントサイドの静的Webアプリ**。サーバー・APIキー・LLM API・
  ログイン一切不要。URLを開くだけで使える(GitHub Pages想定)。
  入力内容は端末外に送信しない(この旨をUIにも明記)。
- 対応環境: iPhone Safari / Windows Chrome・Edge。レスポンシブ
  (`100dvh` + `env(safe-area-inset-bottom)`、入力欄 `font-size:16px` で
  iOSのズーム暴発を防ぐ)。
- **知識はPDF原文に忠実に**。要約で意味を変えない。金額・期間・回数の
  数値基準(下記チートシート)は絶対に改変しない。
- 規約は業界自主ルールで違約金・除名を伴うため、**断定を避ける設計**:
  資料にない事案は「見つからない」と答え、協議会への確認を促す。
  全回答に「参考情報であり最終判断は協議会へ」の注記を付ける。

## ファイル構成(自己完結・共有ファイル不使用)

```
kiyaku-qa/
├── index.html          # 1画面チャットUI(CSSはインライン)
├── js/
│   ├── kiyaku-data.js  # 恒常ルール層: KIYAKU_META, KIYAKU_ENTRIES, QUICK_QUESTIONS
│   ├── sokuho-data.js  # 更新情報層: SOKUHO_ENTRIES(回答速報。追記だけで反映)
│   └── app.js          # 検索エンジン+チャットUI制御
└── docs/
    └── kiyaku-qa-manual.pptx  # スクショ多めの簡易取扱説明書
```

## 2層知識アーキテクチャ(最重要)

1. **恒常ルール層** `kiyaku-data.js` — 規約・施行規則・運用基準解説集から
   抽出した知識。コード修正が必要な変更はここだけ。
2. **更新情報層** `sokuho-data.js` — 協議会が随時発出する「回答速報」等。
   **運営者がテンプレートをコピーして追記するだけで反映**(再ビルド不要)。
   ファイル冒頭に運営者向けの追記手順コメントとテンプレートを必ず残す。
   検索ヒット時は恒常ルールより優先し、黄色枠+「回答速報」タグ+日付で
   回答の先頭に表示する。両者が矛盾する場合は日付の新しい回答速報が優先。

### エントリ形式(両層共通)

```js
{
  id: "unique-id",            // 回答速報は "sokuho-YYYYMMDD-n"
  cat: "カテゴリ表示名",       // 回答速報は date, source も持つ
  q: "代表質問文",             // 関連質問チップにも使う
  keywords: ["同義語", "漢字かなゆれを列挙"],
  verdict: "ok|ng|cond|info", // 提供可/原則不可/条件付き可/解説
  a: "回答本文(です・ます調、根拠を含める)",
  refs: ["規約第○条", "運用基準○-○"],
}
```

## 検索エンジン(app.js)

- LLM不使用のキーワードスコアリング。正規化: 小文字化+カタカナ→ひらがな+
  全角→半角+記号除去。キーワード部分一致で `10 + 長さ×2` 点(長いほど
  specificで高得点)、質問文とのバイグラム一致を最大8点加点。閾値12点。
- 表示: 回答速報ヒット最大2件 → 恒常ルール最大2件 → 「関連する質問」
  チップ3件 → 免責注記。0件時は言い換えの提案+協議会案内。
- verdictバッジ色: ok=緑 / ng=赤 / cond=橙 / info=紺。

## 知識抽出の手順(新規構築・他業界展開時)

1. PDFはスキャン画像のことが多い。`pymupdf`(fitz)で110dpi程度でページを
   PNG化し、Readツールで見開きごとに読み取る(`pdftotext` は文字が取れない)。
2. 読み取りながら**必ずスクラッチパッドの notes.md に条文・数値基準を
   逐次書き出す**(コンテキスト要約対策)。運用基準は「運用基準」欄と
   「解説」欄の両方を拾う。
3. notes.md から60〜80件のQ&Aエントリを作る。1エントリ=実務者の1つの
   疑問(「〜できますか?」)に対応させ、数値基準は必ず本文に入れる。
4. `node` でデータファイルの構文チェック+id重複チェックを行う。

## 数値基準チートシート(医療機器業。検証・レビュー時の照合用)

- 飲食: 情報提供・商談=1万円/説明会・講演会の茶菓弁当=3千円/
  懇親行事・会議後・講師慰労=2万円。二次会・娯楽提供は不可。
- 貸出し: デモ1か月(同一診療科1回)/試用6か月(同1回)/研究12か月/
  故障代替3か月目安/研修1か月。確認書(様式3)5年保存。
- 立会い: 適正使用=1手技1診療科4回・事由から4か月/安全使用=月1回・
  保証期間内かつ12か月。確認書(様式4)5年保存。
- 試用機器: 形状見本=医療担当者1名に1個(縫合糸1セット等)/臨床試用=
  診療科1科に5個(縫合糸2症例分)。試用書(様式1)。既採用先への提供禁止。
- 症例報告報酬: 使用成績調査1万円以内(難件でも3万円以内)/症例。
- アンケート謝礼: 1千円以内の物品・プリペイドカード類(金銭不可)。
- 少額景品: 市価3千円程度まで・金銭代替性なし。製品直結の記念品5千円以内。
- 情報媒体(自社機器に関連しない医学情報): 単価5千円以内目安。
- 違約金: 1回目20〜50万円、2回目50万円超〜100万円。調査非協力10万円以下。

## 検証(必須)

Playwright(`NODE_PATH=$(npm root -g)`、executablePath:
`/opt/pw-browsers/chromium`)で file:// を開き、
1) PC 1280×800 と iPhone 390×844 でスクショ確認、
2) 代表質問(飲食上限/旅行招待→原則不可/無関係な質問→フォールバック)の
   回答テキストをアサートする。

## 取扱説明書(docs/)

pptxスキル(pptxgenjs)で、Playwrightの実画面スクショを多用した
初心者向け簡易マニュアルを作る。構成: 表紙→できること→開き方→
質問のしかた→回答の見方(バッジ凡例)→回答例→見つからないとき・注意→
管理者向け回答速報追記手順。この環境ではLibreOfficeが動かないことが
あるため、視覚QAの代わりに python-pptx でスライド外はみ出し検査+
validate.py+markitdown で確認する。

## やってはいけないこと

- LLM APIや外部サーバーへの依存を追加しない(誰でもURLだけで使える前提)。
- 数値基準・条文番号を記憶で書かない(必ずPDF由来のnotes/既存データと照合)。
- 断定的な法的助言口調にしない。「協議会に確認」の導線を消さない。
- sokuho-data.js の運営者向けコメント・テンプレートを削らない。
- 他アプリ(bucho/jimucho等)の共有JS(/js/)に依存させない。
